# Plan: the dynamic feature (`New list`)

Status: implementation plan for the dynamic feature, the owner's dynamic lists; for the project manager to hand to new sessions. One small pull request per batch, into `main`, in the order
below. Specs read: `2026-11-11-intuitive-editor-design.md` (finding 16 part B, the owner's dynamic-list flow),
`2026-11-11-rows-from-list-plan.md` (part A: `Rows from`, `asRows`, sources, built) and `2026-11-12-inline-block-editing.md` (#413).

## Owner rulings (12 November)

- "That is dynamic lists": `New list` makes the lists that a `Dynamic` block reads with `Rows from`.
- **The design of a dynamic list's own page is the List typed in place, as built today** (`src/InlineList.tsx`, `src/inlineBar.ts`,
  `src/inlineRows.mjs`, PR #401; shared `Inline*` parts in #413). **We do not make a new design of it.** The page reuses the active
  row's dotted outline, the faded empty row, the text button `Add list row`, the floating toolbar and the slots. This plan adds no new
  look, no new layout and no new interaction; each place where something must differ is named below and says why.
- The flow, names and fields of finding 16 stand: `Dynamic` naming, `Edit list`, the fields Icon, Title, Body text, Image, Link and Tags;
  deleting a list asks first and is refused while a block uses it; removing a field keeps its data until the owner confirms.

## What is there today (checked in the code)

- Lists are code: `OwnedList` (`src/schema.ts`) from `standard/*/list.ts` and the apps' `app.json`; `src/site.ts` makes the module
  constants `collections`, `lists`, `icons`, `listsShown(files)`, `listRowsOf(files)`, `listExamples`. 50 files import `collections`.
  `site.lists` is empty by default (`defaults/editor.ts`).
- `asRows` (`{ title, text?, icon?, href?, tags? }`, names of an entry's fields) is on `OwnedList`; `rowLists()` (`src/standard/rows/lists.ts`)
  feeds `Rows from`; on the site `standard.source(id)` (`defaults/standard.ts`) reads `@data/*/*.json` of the list's folder for apps' lists
  and returns `SourceItem[]`; `rowsFromItems` (`src/standard/rows/rows.mjs`) filters by tags and `How many`; `loadRows` runs at build.
  The three views take `ListRow[]`, so no theme changes.
- Tags are the `categories` collection; fields of type `relation` with `to: 'categories'`.

## Data model

**Where.** A list the owner makes has id and folder `<id>`, entries in `src/data/<id>/<slug>.json` (one file per entry, like every other
list), and its definition beside them in `src/data/<id>/_list.json`:

```json
{ "version": 1, "label": "Services", "fields": ["icon", "title", "text", "image", "href", "tags"],
  "dropped": ["image"] }
```

- `fields` is a subset of the fixed set `icon`, `title`, `text`, `image`, `href`, `tags` in that order; `title` is always there. No
  free field types, so the build and `check:content` stay simple (finding 16).
- `dropped` is the field removal not yet confirmed: the field is hidden in the list and in `Rows from`'s field choice, but its data stays in
  every entry until the owner confirms in `Edit list` (then the key is removed from every entry in one commit and from `dropped`). Undo
  before that is just switching the field on again.
- Entry file: `{ "title", "text", "icon", "image", "href", "tags": ["<category slug>"], "order": 3 }`, keys left out when empty; the same names as
  `asRows` expects. `order` as `orderable` lists have it.
- The leading `_` marks the definition. **Every reader of a list's folder skips files whose name starts with `_`** through one helper,
  `isEntryPath` in `lib/ownList.mjs`: the editor's folder lists (`collectionOf`, `slugOf` callers, `Library`), `listRowsOf`, the build's
  glob (`standard.source`), `checkSite`, the trash and history views. Missing one is the main bug to test for (a `_list` row appearing as an
  entry or a page).
- Ids: slug of the label (`slugify`), at most 40 characters, must not equal an existing data folder or collection id (`categories`,
  `testimonials`, `apps`, any app list folder, any `site.collections` folder) nor start with `_`; refused with a plain message. The id never
  changes after creation, so renaming the label changes no file name and no block (blocks store the id in `from`).

**One place, pure code: `lib/ownList.mjs`** (no browser, no React; used by editor, build and check): `FIELDS` (the fixed set with each field's
type, its `asRows` key), `parseDefinition(text)` (returns `{ definition }` or `{ problems }`), `idOf(label, taken)`, `fieldsOf(definition)`
(visible fields: `fields` minus `dropped`), `asRowsOf(definition)` (the generated `asRows`), `entryProblems(definition, data)`,
`dropField(entries, field)`, `isEntryPath`.

**Generated `asRows`.** From the visible fields: `{ title: 'title', text: 'text' if on, icon: 'icon' if on, href: 'href' if on, tags: 'tags'
if on }`. `Image` has no place in a `ListRow` today (the three views take `{ icon, title, text, href }`), so it is not part of `asRows`; it
is kept in the entries and shown on the list's own page, and is picked up by dynamic Cards (finding 17, after the Card block) when
`SourceItem` gets `image`. The generated `asRows` is the same object an app's `app.json` declares, so `rowLists()`, `source`, `rowOf`
and `rowsFromItems` stay as they are, and `Rows from` works unchanged.

**How each reader gets the collections whose fields come from a file.**

- **Editor.** `collections` is a module constant, built from code. A list from a file needs the site's files, so `src/site.ts` gets
  `ownListsOf(files)` (parse every `src/data/*/_list.json`) and `collectionsFor(files)` = the code collections + `collectionOf(definition)`:
  a `FolderCollection` (`kind: 'folder'`, `folder`, `fields` made from `FIELDS` by `fieldsOf`, `slugFrom: 'title'`, `orderable: true`,
  `summary: title`, `asRows`, an icon, the label). The files are already loaded by the app (`RepoFile[]`, as `listsShown(files)` uses them), so
  `App.tsx` computes `collectionsFor(files)` once and passes it down. To keep the 50 importers working, step 1 is **not** to change them: the
  static `collections` stays and means "the code collections"; only the places that must see the owner's lists (`Library`, `MainMenu`,
  `DataForm`, `Media` usage counts, the trash, `BlockSettings` use counts, `Rows from`, `listsShown`, `icons`) switch to `collectionsFor(files)`
  in their own small PRs (batch 3). The `icons` for an own list are one icon (`ListChecks`, the Lists icon) so there is no choice to build.
- **Build.** `standard.source(id)` (`defaults/standard.ts`) falls back, after the app lists, to `@data/<id>/_list.json` + entries: it already
  globs `@data/*/*.json`; it reads the definition with `parseDefinition`, takes `asRowsOf`, skips `_` files. No new build step, and a site
  with no `_list.json` does exactly what it does today.
- **`check:content`** (`src/checkSite.ts`, `scripts/check-content.mjs`): each `_list.json` is parsed (`parseDefinition`: unknown field, no
  `title`, `dropped` not in `fields`, a wrong `version` stop the build with the file path), each entry is checked with `entryProblems` (keys the
  definition has no field for are allowed only for `dropped` fields; `tags` point to existing `categories`; `href` is an existing page or a URL, as
  `rowOf` already decides), and every block with `from: '<id>'` must name a list that exists (a deleted list under a block is a stop, not
  an empty block). Also `casingProblems` already covers folder names.
- **Rows from** (`rowLists()`): `setRowLists(ownedLists)` gets the owner's lists too (their generated `asRows`), so the choice and the tag
  choice appear; the name in the choice is the label. Nothing else in part A changes.

## What the list screen is: existing, and new plumbing

The list's own page (`#list/<id>`) shows **the existing `InlineList` component** (`src/InlineList.tsx`) drawing the entries as the site draws the
List block, typed in place. It is not a new design. What is new is only the plumbing that makes the component work outside a ProseMirror node view.

| Part | Status |
| ---- | ------ |
| Rows drawn as the theme's List, active row dotted outline, no background, faded empty row, text button `Add list row`, Enter and Backspace keys, slots before and after the text | **existing**: `InlineList.tsx`, `inlineRows.mjs`, CSS of #401, reused unchanged |
| Floating toolbar: `Add above`, `Add below`, `Move up`, `Move down`; the compact `Row` menu on a phone | **existing**: `inlineBar.ts`. New: a host that mounts it outside the editor (below); the block menu (Hide, Move, Remove) is replaced by one list menu (`Edit list`, `Delete list`), because there is no block |
| Icon slot, Link slot (the sheets they open) | **existing** (`onIcon`, `onSettings`, the icon picker of #409 and the link sheet) |
| Image slot and Tags slot on the active row | **existing pattern, new slots**: the `Inline*` parts of #413 (`InlineSlot`, `InlineField`) and the card's Media slot for the image; Tags opens the existing tag relation picker (with `Create a tag`). Same dotted/slot look; shown only for the fields the list has |
| State (`items`, `active`, `focus`) | **new**: today a node view in `MarkdownEditor.tsx` keeps it as block props. New `src/OwnListPage.tsx` keeps it in a small reducer over `inlineRows.mjs` and maps rows to entries |
| Row ↔ file | **new**: one row is one entry file (`entryOfRow`/`rowOfEntry` in `lib/ownList.mjs`, tested). A row first typed creates the file (slug from the title, `slugFrom: 'title'`, collisions get `-2`); the faded empty row is not a file; a completely empty row is not saved; the slug never changes when the title does. `Move up` and `Move down` rewrite `order` of the two entries; `Remove` deletes the file and offers `Undo` through the existing trash (`Deleted.tsx`) |
| Saving | **new wiring, existing mechanism**: autosave per entry as pages do (`autosave-form` flow), with the existing "saved/saving" state of the form frame. To check at the start of batch 5: that a move (two files) can be one commit through the Worker's commit proxy; if not, two sequential commits with the second only after the first |
| `Edit list` / the list's settings (name, fields, delete) | **new, a sheet, not a screen**: a sheet in the existing sheet style with the name and the six field switches (`Title` locked on), `Delete list` at the bottom. No new layout |
| Menu: `Lists` screen gets `New list` | **new**: a FAB/button on the existing `Lists` screen (`Library.tsx` `Lists`), opening a small dialog: name, then the field switches; creates `_list.json` and opens the list page with the first faded empty row active |

What is not new: no table, no separate form per entry, no card grid, no extra tabs. An owner who knows the List block types a dynamic list the same way.
If a part of this table turns out to need a look of its own, the session stops and asks the owner instead of designing it.

## Risks for existing sites (Sara's site: no content may change)

- **No file of an existing site is written, moved or migrated.** A list exists only when `src/data/<id>/_list.json` exists, and only `New list` (batch 7)
  writes one. Until then every new reader takes the old path; batch 3's test proves `collectionsFor`, `listsShown`, `listRowsOf` and `check:content`
  are the same on the demo and the starter.
- **`_` files in a data folder** could be read as entries by code not on the list above (a site's own `import.meta.glob('@data/*/*.json')`, an
  app's reader, the Worker's backup or search). Grep for `data/*/*.json` and `listRowsOf`-style globs in `lib/`, `worker/`, `site/`, `bin/` and the
  apps' code at the start of batch 3 and cover each by `isEntryPath` or a test. The definition is written only into a folder the owner's new list
  creates, never into an existing folder, so an existing list can never gain a `_list.json` (the id check refuses an existing folder).
- **Name clash with a folder a site already has** (a site's own `src/data/services/` for a hand-made list). The id check reads the folder names of the
  site's files, so `New list` named Services is refused or offered `services-2`; it never adopts an existing folder.
- **`collections` stays a static constant**: replacing it would touch 50 files and risk every screen. The plan only adds `collectionsFor(files)` and
  moves the few screens that must see own lists, one PR each; a screen left behind merely does not show own lists (safe, no data loss).
- **A block under a deleted list**: refused while a block uses it; if someone deletes the folder by hand, `check:content` stops the build with the block's page
  and list id (not a silent empty block). This is a new stop, but only for a site that has own lists.
- **Field removal and data**: `dropped` keeps data; only the confirm step rewrites entries, in one commit, with a list of changed files so a revert is one step.
- **Worker rule** (CLAUDE.md): no change to `worker/*.js` is planned; if a multi-file commit needs one, no pending I/O promise in module memory.
- **Theme and `Rows from`**: the three views stay unchanged, so every theme works the same day; `Image` shows only on the list's own page until dynamic Cards.
- **Version rule**: batches 2 to 6 are `patch`/empty. Anything that makes the owner-visible `New list` appear on `main` before 0.15.1 breaks the `main`
  rule (patch or empty only) unless it is `minor` and the owner agrees; this is why batch 7 is last and separate.
- **#413 is not touched.** If it merges first, batch 5 uses its parts; if the owner changes its shape, batch 5 follows it. Batches 2 to 4 and 6 do not import the `Inline*` parts of #413.

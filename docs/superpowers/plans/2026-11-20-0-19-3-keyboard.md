# 0.19.3 The editor by keyboard (plan)

Status: **approved, 20 November 2026.** The owner decided the text bar's key (*Decision*); the rest follows the owner's rule of 19 November 2026 that the sites and the editor meet **WCAG 2.2
level AA** and that WCAG wins where Material 3 differs (`CLAUDE.md`, *Accessibility: WCAG 2.2 AA*). Roadmap: `plans/2026-11-14-roadmap-0-18-to-0-24.md`,
item 0.19.3: "Every main flow of the editor done with the keyboard alone: focus order, no focus trap, focus never hidden behind a bar or
sheet, and a check that walks the flows by keyboard."

## What 0.19.3 is

A check that walks the editor by keyboard, run in CI and failing on a problem that is not on its allowlist, released together with the
fixes that make it pass. A check and the fixes that make it pass are one bite (`plans/2026-11-18-release-per-feature.md`), so 0.19.3 is one
feature, `feature/0.19.3-keyboard`, cut from `main` by PM 0.19.3 once 0.19.2 is released (it builds on 0.19.2's fixes to the same parts).

The WCAG criteria it covers: 2.1.1 Keyboard, 2.1.2 No Keyboard Trap, 2.4.1 Bypass Blocks, 2.4.3 Focus Order, 2.4.7 Focus Visible, 2.4.11
Focus Not Obscured (Minimum), and 3.2.1 On Focus for focus that is lost when something opens or closes.

Not in 0.19.3: the axe scan and its fixes (0.19.2, which already makes the carousel and the bottom sheet's content focusable and an
`aria-hidden` block preview `inert`), what a screen reader says (0.19.4), the small UI fixes (0.19.5). The site's own keyboard use is
`check-popup-focus.mjs`'s and stays as it is.

## The main flows

The roadmap names "every main flow" and nothing defined them. These are they, each walked from the start screen with Tab, Shift+Tab,
Enter, Space, Escape and the arrow keys only:

| Flow | From → to |
| --- | --- |
| A. Write | start screen → open a page from Pages → into the text → type → Save changes |
| B. Blocks | in a page: insert a block from the search sheet → move it up and down → open its settings → remove it |
| C. Format | in the text: reach the text bar → Bold, a style, a list, a link → back to the text |
| D. Page settings | open the page's settings sections → change a field → Schedule dialog → close with Escape |
| E. Images | an image field → its side sheet → Change image → the library → choose → back where it started |
| F. Menus | every editor menu: open with Enter or Space, move with the arrow keys, choose with Enter, close with Escape |
| G. Lists and search | Pages, Blog posts, Media: search, sort, filter, open a row, select rows |
| H. Settings | a settings screen (Business, Colours, SEO and Redirects): every field, tab and switch |
| I. Dashboard | Edit dashboard → move a widget up and down → done |

## The audit it starts from

The CTO ran a keyboard audit once on `main` at 511105c3 (20 November 2026; Playwright, nothing committed). It is the baseline this plan fixes.

- **The Tab walk:** 306 editor screens (the editor's own `#` links, as 0.19.2's scan finds them), at 1280 and 375 px: 612 runs, 13,972 Tab
  presses, 139 s on 3 workers. Each focus stop was tested for being visible, covered, showing a focus indicator, trapping and order.
- **The flow probes:** flows A to F above, by hand in a script, at 1280 px.

What the Tab walk found:

| Problem | Nodes | Where | Cause |
| --- | --- | --- | --- |
| Trap (2.1.2) | 0 | | |
| Covered by a bar (2.4.11) | 18 on 10 runs | the save bar over the last fields of a new page or post (1280 and 375); the media file toolbar over fields on `files/images/…` (375); the photo credit tooltip over its own Close (start screen, 375) | no `scroll-padding-bottom` for the sticky bars (`src/editor.css:400-418`, `src/editor-screens.css:742`); the tooltip (`src/UpdatesNotice.tsx:76`, `src/editor-screens.css:111-115`) |
| Focus off the visible part (2.4.7) | 118 on 4 runs | the header and footer previews on Global | the preview `<iframe>` (`src/ui.tsx:4007`) puts the whole demo page in the Tab order, about 60 stops, half outside the cut, and the frame itself takes focus with no ring |
| No focus ring (2.4.7) | 4 | the tab panel (`company/colors` and others) | `.mo-editor-focus-quiet-visible:focus-visible { outline-style: none }` (`src/editor-ui.css:38-41`) on a panel that is a Tab stop (`src/ui.tsx:3793`) |
| No skip link (2.4.1) | all page screens | 7 to 34 stops (median 23), mostly the navigation drawer, before the text | nothing to jump over them |

The page's text and title show only the caret when focused (the audit hid the caret, so they are not counted); 0.19.3 checks them with the
caret on. 36 "mouse-only" hits were decorative button previews and are not problems.

What the flow probes found:

- **A. Write: passes, but focus is lost twice.** Opening a page from the list drops focus to `body`, and so does Save changes.
- **B. Blocks: fails.** Insert, Move up and Move down work. Remove is only in the bar's block group, which shows only while a card is
  selected, and Shift+Tab to the bar passes through the text, which clears it. No arrow key selects a card.
- **C. Format: fails.** The text bar's tools (Bold, Italic, Style, List, Align, Link) unmount when the text loses focus
  (`src/MarkdownEditor.tsx:2430`, `setInText(view.hasFocus())`; the group at `:3264`), so Tab can never reach them, and Shift+Tab from the text
  drops focus to `body`.
- **D. Page settings: passes.** The Schedule dialog starts on Cancel, and Escape gives focus back to Schedule.
- **E. Images: passes.** Focus comes back to Change image and then to the card. Business › Logo opens only the native file chooser.
- **F. Menus: fail.** The editor's `Menu` (`src/ui.tsx:2127`, 44 uses) moves focus into the menu and handles the arrow keys only when it is
  `attached` (a field's dropdown, one use). Every other menu (the page's More, a row's actions) keeps focus on its button when it opens,
  makes every item a Tab stop, ignores the arrow keys, and drops focus to `body` on Escape. The theme's menu (`theme/ui/Menu.tsx`, the site's)
  already does it right.
- **I. Dashboard: passes, but focus is lost first.** Edit dashboard unmounts itself when pressed (`src/DashboardGrid.tsx:114-118`).

So most of the work is a few shared parts: the menu, the text bar, focus after something opens or closes, and scroll padding for the bars.

## Decision

**How the keyboard reaches the text bar.** The bar can't be a Tab stop after the text without making every Tab leave the text. Editors solve
this with a shortcut from the text into its toolbar. **Decided** (owner, 20 November 2026: "Yes"): **Alt+F10** moves focus from the text to the bar's first tool,
the arrow keys move between its tools (one Tab stop, the ARIA toolbar pattern), and Escape goes back to the text where the cursor was. It is
the shortcut TinyMCE and CKEditor use, so screen reader users already know it (0.19.4 announces it). The bar stays shown while
focus is in it. The editor's own workspace is outside Material 3 (owner, 13 Nov), so no deviation is recorded.


## The check

- `npm run check:keyboard` (`scripts/check-keyboard.mjs`), Playwright on the built demo with `openEditor` and `serveBuilt`
  (`scripts/built-site.mjs`), no new dependency.
- **The Tab walk:** every screen `check:screens` opens, at 1280 and 375 px, inside the existing `screens` shards like 0.19.2's `check:a11y`
  (the screen is already open; about 0.2 s per screen and width), not a new job. From the top, up to 150 Tab presses or until focus comes back
  round. It fails on:
  - a **trap**: the walk cycles among a few elements and never comes round;
  - **covered focus**: after the browser scrolls it into view, the focused element is entirely covered by another one
    (`document.elementsFromPoint` at its centre and four inset points);
  - **invisible focus**: the focused element has no size, is hidden, or lies outside its scroll container's visible part;
  - **no indicator**: nothing changes on the element, its `::before`/`::after`, or up to three ancestors (`:focus-within`) between focused
    and not focused; text fields are compared with the caret shown;
  - **lost focus**: focus lands on `body` before the walk comes round.
- **The flows:** A to I above as scripted walks (`scripts/keyboard-flows.mjs`), at 1280 px, and A, B and F at 375 px, in the shard that holds
  their start screen. A flow fails when a step's control can't be reached by keyboard, or when focus is on `body` after something opens or
  closes. After closing it must be on the control that opened it, or on the next sensible one where that control is gone (named in the
  flow).
- **Allowlist** `scripts/keyboard-allowlist.json`: entries of problem, screen and selector, and reason, like `scripts/a11y-allowlist.json`. It
  fails on a problem not on it and on an entry that no longer matches, so it only shrinks. At release it is empty, unless the owner has approved
  an entry.
- `.claude/skills/checks/SKILL.md` says when to run it (a change to an editor screen, a sheet, a dialog, a menu or the bars).

## Batches (pull requests into `feature/0.19.3-keyboard`)

1. **The version and the check.** Sets the version to 0.19.3 (`plans/2026-11-19-version-at-feature-start.md`), adds `check:keyboard`, the
   flows, their CI steps and the allowlist holding exactly the baseline found then (it may differ from the audit's after 0.19.2). CI green. Each
   later batch removes its entries.
2. **Menus.** The editor's `Menu` gets the theme menu's keyboard behaviour in every mode, not only `attached`: focus goes into the menu when it
   opens (the first item when opened by keyboard), one Tab stop with the arrow keys, Home, End and a letter between items, Enter and Space
   choose, and Escape or Tab closes it and gives focus back to its button. On a phone, where it is a bottom sheet, the same focus return.
   Flow F.
3. **Focus after open and close.** Opening a page or post from a list puts focus on its title (A). After Save changes focus stays on the
   button or, if it goes, on the text (A). Edit dashboard and Done keep focus on the control that replaces them (I). Every sheet and dialog
   gives focus back to what opened it, or to the next row when that is gone (a removed block, a deleted row). A shared helper, used by
   `Menu`, the sheets and `ask()`, so it is made once.
4. **The text bar and blocks.** Alt+F10 and the toolbar pattern, as decided above; the bar stays shown while focus is in
   it (C). A block card can be selected by keyboard (Enter or Space on the card, and Escape back to the text), which shows the bar's block
   group with Remove, and Delete removes the selected card as Remove does (B).
5. **Covered and invisible focus.** `scroll-padding-bottom` for the save bar and the media file toolbar, and `scroll-padding-top` for the
   editor's top bar, from the bars' own heights (a shared custom property, not a number per screen). The photo credit tooltip no longer covers
   its Close. The header and footer preview `<iframe>` leaves the Tab order (`tabindex="-1"` and its content `inert`: it is a picture of the
   site, not a place to work). The tab panel keeps its ring, or stops being a Tab stop when its first control takes focus.
6. **Skip link.** A *Skip to content* link, first in the Tab order and shown only when it has focus, jumps over the navigation drawer to the
   screen's main content (the text on a page screen). New text in `en-US` and `da-DK` (skill `site-editor-writing`).

Batch 1 goes first. Batches 2, 5 and 6 touch different files and can run side by side. 3 follows 2 (it uses the helper with the menu), and 4
goes last (it touches the text area, which 3 also touches). Every batch removes the allowlist entries it fixes, keeps `check:screens`,
`check:a11y` and `check:contrast` green, adds no text without its Danish version (`check:language`), and adds a release note line where a site
owner notices it (skill `release-notes`: the shortcut, the skip link and the menus are noticed).

## Done when

`check:keyboard` runs in CI on every pull request with its flows, its allowlist is empty (or holds only entries the owner approved), the owner
has reviewed the feature on the demo by keyboard, and 0.19.3 has run on staging before the owner releases it.

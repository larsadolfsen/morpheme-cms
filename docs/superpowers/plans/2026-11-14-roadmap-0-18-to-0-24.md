## 0.20 Component steps

Owner, 19 November 2026: its own line after Build speed, split into features released one at a time. A spec comes first,
written by the CTO and approved by the owner; it sets the order below:

1. **The steps table and its checks.** The source table, the tokens and the `mo-*` classes it generates (`mo-elevation-N`,
   `mo-state-layer`), and checks that fail on raw shadows, radii, durations and pixel spacing and name the step. No
   contract change.
2. **The developer guide.** Generated from the table into the npm package, with typed class and token names.
3. **Component levels.** Each component's level as a number that expands into its `--mo-comp-*` tokens, stored by the
   customizer. The only part that changes the contract: contract 9 (`THEME_API`, `APP_API`; a new contract is never major).
4. **Templates and screenshots.** `morpheme new block | app | theme` and one screenshot command.

Standardized steps instead of free values, so developers and LLMs (vibe coding) can build on Morpheme without going wrong.
A step sets several values at once.

- **Elevation as the example.** An M3 level sets the tonal surface and the shadow together
  (`--mo-sys-elevation-levelN-color` and `-shadow`), and hover and drag go one level up. Today there is no elevation class;
  parts read the tokens in their own rules.
- **`mo-elevation-N`.** A plain class (like `mo-type-*`, not Tailwind) that sets the background and the shadow together,
  perhaps with the on-surface text colour. Only for plain elements, never for M3 parts: a class wins the cascade and would
  freeze a part's hover and drag level.
- **The customizer** stores a level as a number per component ("Top app bar: level 2", not a raw shadow). The number expands
  into the component's `--mo-comp-*` tokens (colour, shadow, hover at level + 1), the component-token direction of
  `docs/superpowers/specs/2026-11-17-list-to-cards-design.md`.
- **The same pattern** for colour roles (container and on-container pairs, as section colours already are), the type scale
  (`mo-type-*`, already bundled), shape (the corner scale; Expressive changes shape on press), motion (the springs: fast,
  default and slow, spatial and effects), density, and state layers (fixed by M3, so not customizable, but a
  `mo-state-layer` class would help). One design, "component steps", rather than six features.

The recommendations, in priority order:

1. One machine-readable source table of every step, which generates the CSS tokens, the `mo-*` classes, the customizer's
   options, the docs and the checks.
2. Components first; classes only as glue for plain elements, stated loudly so an LLM doesn't rebuild a card from classes.
3. Checks that say what to use instead: fail on raw shadows, radii, durations and pixel spacing with "Use
   `mo-elevation-2`", as `check:editor-colors` and `check:phosphor` already do for their cases.
4. A short developer guide in the npm package, generated from the table (every class, component and token, one example
   each), for the AI of site, theme and app developers.
5. Typed class and token names, so a typo fails the type check.
6. Templates: `morpheme new block | app | theme` gives a skeleton that already passes every check.
7. One command that shows a screenshot of a change.

Items 1 and 3 do most of the work; they build on the class vocabulary that the Tailwind removal (0.18.2, contract 7) rebuilds.

## 0.23 Screens: app bars, sheets and autosave

Every screen gets M3's app bars, and settings screens become sheets that save the way a page does.

- **App bars on every screen** (owner decisions, 14 November; read from m3.material.io/components/app-bars the same
  day). Owner questions open (proposals P1–P8): `specs/2026-11-14-app-bars-design.md`.
  - **Search app bar** on the start screen and the list screens ("Search pages"). The search field moves up from
    today's search row. The sort, filter and date buttons become a row of chips under the bar.
  - **Pages and Posts open with the search bar shown.**
  - **Small app bar** on the page being written: back, the title, the search icon and Publish. No overflow menu in the
    app bar; the writing tools stay in the toolbar.
  - **Medium flexible app bar** on detail screens and the side sheet's header.
  - The search icon of 0.18 becomes the search app bar here.
  - The search-row rule in `morpheme-website`'s `CLAUDE.md` (*Søgeknapper*) changes with it.

- **Settings pages open as a subpage or a side sheet** (owner decisions, 14 November; full-screen sheets are not Material 3
  and bottom sheets are for menus and supplementary content):
  - On a phone (compact), a **subpage with a back arrow** (app bar: back arrow and headline only), and **Save** in the bottom bar the page form uses. No autosave.
  - On medium and expanded widths, a **side sheet** next to the page, with **Save** and **Cancel**. No autosave.
  - Leaving with unsaved changes (back arrow, browser back, Cancel) asks with the existing "Keep your changes?" dialog.
  - The same pattern is used for a file in Files (0.18).
  - While the owner types, a hidden copy is kept in the browser on that device. It is offered back ("Restore your unsaved
    changes?") only if the form closed without Save or Cancel. Save or Cancel deletes it.
  - Owner questions open (O1 which forms, O2 standard or modal side sheet; proposal P1): `specs/2026-11-14-settings-sheets-design.md`.
- **Autosave everywhere, phase 2.** `specs/2026-11-14-autosave-everywhere-design.md`. Decisions 1 (waiting versions in
  R2 only, never git) and 7 (Remove field and Remove data wait for the final Save) are agreed. Owner questions open (2–6
  and 8–10). Its scope is redrawn around the sheets (its section 0 and build plan 5a, 14 November); question 11 added.
- **Dashboard leftovers**, if the owner wants them. `specs/2026-11-07-dashboard-widgets-design.md` (agreed

## How the lines run

- `0.18` was cut from `main`. Each later line's branch is cut from the previous line's branch when its work starts:
  `0.19` was cut from `0.18` on 14 Nov 2026, before 0.19 became Build speed; from 0.19 each feature is a branch from `main` (section *From 0.19: a release
  per feature*).
- `0.18` is merged into `0.19` after each merge into `0.18`. `0.19` is never merged into `0.18` or `main` until 0.17 and
  0.18 are released and the owner says go.
- While 0.17 is unreleased, `main` is merged into `0.18` after each merge into `main`.
- After each release, `main` is merged into the next line.
- The levels each branch allows: skill `changesets`.

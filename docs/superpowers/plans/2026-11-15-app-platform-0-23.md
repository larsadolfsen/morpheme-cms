# 0.23 App platform: the release plan

> **Status:** planning with the owner, 15 November 2026 (a planning session: nothing is built). This file collects the
> owner's decisions for 0.23 and the specs the release needs. Each spec gets its own plan when it is ready.

**Goal:** apps can do more, safely: server code runs in a sandbox, apps keep visitor data in a database, apps offer
services to other apps, and Forms proves the last two with a real feature.

## Decisions (owner, 15 November 2026)

1. **Server code needs the Workers Paid plan on Cloudflare.** The sandbox uses Cloudflare Dynamic Workers, which are
   only on Workers Paid ($5 a month per account; developers.cloudflare.com/dynamic-workers/pricing). An app with a
   `worker.js` cannot be turned on in a site on the Free plan, and the editor and the store say why. Apps without server
   code work on every plan. The sandbox is written behind a small interface of the CMS's own, so other hosting
   platforms can implement it later (the owner will open up for more platforms).
2. **Every app's server code runs in the sandbox, Morpheme's too** (paid store, decision 8). The `FIRST_PARTY`
   exemption ends in 0.23. Cookiescanner, which runs a browser (Playwright) in its `worker.js`, must work from inside
   the sandbox; spec 1 says how (a scoped browser binding stub, **verify** that Browser Rendering can be handed over).
3. **Forms is in 0.23**, as the first real user of storage and providers, so neither foundation ships tested only on
   fixtures.
4. **The Unsplash app uses Morpheme's Unsplash key through the store** (the store's `/api/unsplash/*` proxy, which
   already takes a site's store key and caches). The owner sets nothing up. All sites share Morpheme's Unsplash rate
   limit, so the key needs Unsplash's production approval. The CMS's media providers today take an owner's key
   (`needsKey`); spec 5 adds a provider that authenticates with the site's store key instead.
5. **One app contract, 7, for everything 0.23 adds to `app.json`** (storage, `provides` / `uses` / `needs`, the sandbox
   rules, Forms' keys if any). Contract 6 is 0.19's (`lists`). The paid store's keys (`paused`, `plans`) become contract
   8 in 0.25.

6. **Forms is a core feature, not an app**, so forms work on every plan, as in WordPress. The form block and the
   submission handling are the CMS's own. Receivers declared as data (Mailchimp) also work on the Free plan; only a
   receiver with code (`worker.js`, for example SMTP) needs Workers Paid (decision 1).
7. **App data gets its own D1 database, `APP_DATA`**, apart from `CONSENT` (storage spec, decision 1 and open
   question 3): visitors' answers never sit beside sealed sign-in tokens.
8. **An existing site turns storage on when the editor asks** (replaced by decision 29): it says what it changes in the Worker's settings and
   commits it after the owner's yes (storage spec, open question 4).
9. **The storage limits stand as proposed**: 50 000 rows and 256 KB per row per table, 1 000 000 rows per site;
   personal data kept 365 days by default, at most 730, and the owner can only shorten it (storage spec, open questions
   1 and 2). D1's Free-plan write limits get no warning of their own: a refused write shows as a problem on the app's
   page, like a quota (open question 5).

10. **Forms can email the owner out of the box.** A built-in receiver in the CMS sends the answers to the owner's
    address with Cloudflare's own email sending (Email Routing's `send_email` to a verified address, free; **verify**
    in the Forms spec). This is the built-in provider rule of the providers spec (its decision 9, open question 3):
    it stays. Apps add more receivers (Mailchimp first).
11. **Spam protection is Cloudflare Turnstile plus a honeypot field and a rate limit per visitor.** Turnstile adds its
    host to the form pages' CSP (`lib/csp.mjs`), and the cookie banner's texts must say what it does (**verify** whether
    Turnstile needs consent).
12. **Third-party providers may have server code**, run in the sandbox, reaching only the hosts in their `csp`, on
    Workers Paid (decision 1). Data-only providers (a request template) work on every plan. This answers the providers
    spec's open question 2; its decision 8 ("code is for first-party apps") is replaced.
13. **The sandbox's limits are measured, not guessed.** The sandbox spec runs the real apps (Cookiescanner, Mailchimp,
    a form receiver) on `morpheme-staging` and proposes `cpuMs` and `subRequests` with headroom; the owner approves the
    numbers there.

14. **The CMS is born with basic built-in versions, and apps can replace them** (owner, after decision 2). Every
    function a site needs to work (forms that email the owner, the cookie banner with a cookie list kept by hand, site
    search, the image picker with the site's own images) has a built-in version in the core that needs no app server
    code, so it works on every plan. The sandbox is kept on every plan: app server code always runs in it, Morpheme's
    too, and needs Workers Paid. An app can **replace** a built-in where only one can be active (search: after asking,
    as the one-app types do) or **add to** it where several can (form receivers). When the app is removed, turned off
    or paused (a lapsed subscription, 0.25), the built-in takes over again, so a site never loses a basic function.
    This makes the providers spec's built-in provider rule (its decision 9) central, not optional. Cookiescanner stays
    an app and needs Workers Paid: the cookie banner and list are the built-in, the scanner fills the list for you.
15. **What Cloudflare offers for free is built in; another supplier is an app** (owner). The built-ins (decision 14)
    use the site's own Cloudflare services where they are free: email sending to the owner's verified address (Email
    Routing's `send_email`), Turnstile, D1, R2, image handling. Sending or doing the same through any other supplier
    (SMTP, Mailgun, SendGrid, Brevo, …) is a connector app that replaces or adds to the built-in. **Verify** in the
    Forms spec whether email to visitors (a confirmation to the person who sent the form) is free with Cloudflare's
    Email Service; if not, it is an app too.

16. **A site's own apps are trusted.** An app written for one site and kept in its repository (not installed from the
    store, such as Sara's own app) runs its server code directly in the site's Worker on every plan, as today. The
    sandbox protects a site from code it did not write; decision 2 is about apps from the store.
17. **On the Free plan, a store app's server part pauses when 0.23 arrives.** A site that already has a store app with
    server code (Cookiescanner) keeps the rest of the app (for Cookiescanner, the cookie list); the server part stops,
    and the editor says it needs Workers Paid, with a link to upgrade. Nothing is deleted, and upgrading turns it back
    on.
18. **Forms launches with the basic fields**: text, email, phone, long text, number, date, checkbox, choice (dropdown
    or radio buttons) and a consent checkbox. No file upload at launch.
19. **Site search is not in 0.23.** It is a built-in (decision 14), but a large feature of its own (an index at build
    time, a search block, a results page) with its own spec in a later version.

20. **An app's server code has its own list of hosts.** `app.json` gets a list of the hosts its server code may reach,
    apart from `csp` (what visitors' browsers may load). A host the server needs is never opened in visitors' browsers,
    and the reverse. The sandbox's outbound gateway allows only that list (contract 7).
21. **A failing app is shown, not stopped.** When an app's server code fails (an error, or over its CPU or request
    limits), the problem shows on the app's page and the owner gets a notification. The app stays on while the owner
    can act (escalation: decision 34). Work that must not be lost is saved before the app runs (a form's answer is in
    storage before any receiver gets it).
22. **Forms are built like the owner's own lists, then placed with a block.** The Forms screen has a builder modelled on
    the new-list builder (`src/NewListDialog.tsx`, `lib/ownList.mjs`): the owner names a form and adds its fields
    (decision 18), and the form's definition is a file in the site's repository, as a list's `_list.json` is. A Form
    block picks one of the site's forms, as a list block picks a list, so one form can sit on several pages.
23. **The owner reads the answers on the Forms screen.** Each form lists its answers, newest first, with search, delete
    and CSV export. The answers stay in `APP_DATA`, never in the repository.

24. **After sending, the owner chooses per form what the visitor sees:** a thank-you message in place of the form (the
    default) or a page of the site.
25. **The owner hears of a new answer by email and in the editor.** A new form has the built-in email receiver on, to the
    owner's address (decision 10); the Forms screen shows a count of unread answers.
26. **The Unsplash app follows Unsplash's rule and hotlinks.** Its images stay on Unsplash's servers (their host in the
    pages' CSP), and cropping uses Unsplash's own resize parameters; the site keeps no copy. This differs from the image
    picker today, which copies a chosen image into the site, so spec 5 says how a provider marks its images as hotlinked.
    **Verify** the rule in Unsplash's API guidelines before spec 5; it is needed for the production approval
    (decision 4).

27. **A store app's server code needs a contract-7 version.** An app released before 0.23 has no server hosts list
    (decision 20), so its server part pauses until its publisher releases a contract-7 version (the rest of the app
    keeps working, as in decision 17). Only Morpheme publishes today: Cookiescanner is released on contract 7 with 0.23,
    so no site notices.
28. **Turnstile is always on.** Every form has it; there is no switch per form.
29. **The 0.23 update gives every site its `APP_DATA` database,** whether it uses forms or not. This replaces decision
    8: the update to 0.23 adds the binding to the site's Worker settings, and the editor no longer asks per app.
    **Verify** that Cloudflare creates the database on deploy from a binding without an id (automatic provisioning),
    and say what the update shows the owner before it is applied.
30. **AI assistants never read form answers.** The site's MCP server (`worker/mcp.js`) sees the forms' definitions,
    not the answers; answers are only on the Forms screen and in its CSV export.

31. **The email about a new answer holds the whole answer** (every field), with a link to it on the Forms screen, so the
    owner can reply straight away.
32. **Unsplash's credit shows automatically.** The theme draws a small "Photo by … on Unsplash" on every Unsplash
    image, and the owner cannot remove it, so every site keeps Unsplash's rules (spec 5; the credit is already saved in
    the image's record).
33. **A visitor's data is deleted by email address.** On the Forms screen the owner enters an address and deletes every
    answer that holds it, across all forms, in one step (GDPR erasure).

34. **A failure nobody acts on escalates** (owner, after decision 21). Day 0: the problem on the app's page and an
    editor notification. Still failing after 24 hours: an email to the owner. Still failing after 7 days: the app's
    server part pauses, the built-in takes over (decision 14), and the owner is told. Nothing is deleted, and one click
    turns it back on. The clock restarts when the app works again or the owner turns it back on.
35. **The publisher hears of failures as counts.** The store tells an app's publisher how many sites see it fail, with
    the error type and the app version; never site names or visitor data. Spec 1 says how the site reports it to the
    store.

36. **Without Email Routing, forms still work.** Answers are saved and shown on the Forms screen with the unread count,
    and nothing is emailed; the editor says why and that an email app can be installed.
37. **A confirmation email to the visitor is an app** (D15): it is not free on Cloudflare. The core sends nothing to
    visitors.
38. **A data receiver pauses too.** A provider without server code (Mailchimp) follows the same escalation (D34): after 7
    days of failures its sends stop until the owner turns it back on. Answers are saved first.
39. **A new form starts as a contact form:** Name, Email, Message and a consent checkbox, which the owner can change or
    remove.
40. **Erase by email covers all personal data,** apps' tables too, not only forms (extends D33). The owner sees the counts
    per table before deleting.
41. **No size cap of our own, but warnings in good time.** At 80 % and 95 % of D1's database size, the owner gets a
    notification and a line on the Forms screen and the apps' pages, with what each app uses and the advice to upgrade
    to Workers Paid or delete old data.
42. **The 0.23 update applies automatically,** as every CMS update, though it changes the Worker's settings (D29); the
    release note says what changes, and a failed build undoes it.
43. **A provider's secret key is sealed in D1** (a field type `secret`), as the image providers' keys are: never in the
    repository, never given to the app's code, never shown again.
